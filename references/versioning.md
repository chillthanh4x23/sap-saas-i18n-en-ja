# Skill versioning and releases

The package uses local Git history, [Semantic Versioning](https://semver.org/spec/v2.0.0.html) and a [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) change history. `VERSION` is the single maintained package version. Git records individual changes; an annotated `vX.Y.Z` tag identifies a released snapshot.

Versioning covers this skill folder, including instructions, terminology, scripts, tests, assets and UI metadata. Workspace sources, translation runs, application-specific run profiles and external wording catalogs are outside this repository. A skill version identifies a method and its bundled data; it is not an accuracy score or approval of every glossary entry.

## Compatibility and version numbers

The compatibility contract includes the skill name and invocation behavior, supported resource formats, documented script arguments and exit codes, and documented profile/report fields. Translation-policy and terminology changes must also be recorded because they can affect Japanese output without changing a script interface. Existing JSON `schemaVersion` fields describe their data format; they are not package versions and must not be bumped just to match `VERSION`.

| Change | Version rule | Example |
|---|---|---|
| Compatible correction or clarification | Increase PATCH | `0.2.0` → `0.2.1` |
| Added capability or intentional translation-policy/default change | Increase MINOR, reset PATCH | `0.2.1` → `0.3.0` |
| Incompatible contract change during initial development | Increase MINOR and document migration | `0.3.0` → `0.4.0` |
| First declared stable contract | Release `1.0.0` | Requires an explicit stability decision, not just a passing test suite |
| Incompatible contract change after `1.0.0` | Increase MAJOR, reset MINOR/PATCH | `1.2.3` → `2.0.0` |

The pre-1.0 rules are this package's development convention; Semantic Versioning does not promise stability for `0.y.z`. A terminology change that alters intended defaults belongs in a minor release; a correction that makes an existing rule behave as already documented can be a patch. Explain material output changes in the changelog even when no command-line interface changes.

## Normal maintenance

Keep work on `main` for small changes; use a short-lived branch for a substantial feature or experiment. Use a clear commit message such as `fix: preserve repeated placeholders` or `docs: clarify terminology evidence`. Collect notable changes under `[Unreleased]`; a commit does not require a new release number.

Before a release:

1. Review the changes and choose the version using the table above. Update `VERSION`, and move the relevant `[Unreleased]` notes into a dated `X.Y.Z` entry in `CHANGELOG.md`.
2. Run the checks appropriate to the changes. For a package baseline or script change, run the Python and Node tests below. For terminology changes, follow the existing [library workflow](library-workflow.md) to regenerate and review affected reading views. Run the installed skill-creator validator when available; disclose any unavailable check.
3. Confirm that no private data, local settings or generated results are staged, then commit the reviewed release changes.
4. Create an annotated tag matching `VERSION`. Released tags are immutable: correct a release with a new commit and version, rather than moving or deleting the old tag.

Commands below run from the skill folder. Use a working Python interpreter for the environment; this workspace's bundled interpreter is also suitable. `-B` prevents generated bytecode from entering the package.

```text
python -B -X utf8 -m unittest discover -s tests -p "test_*.py"
node --test tests/validate-i18n.test.mjs
git diff --check
git status --short
git add -- <reviewed-paths>
git diff --cached --stat
git commit -m "chore: release 0.2.1"
git tag -a v0.2.1 -m "Release 0.2.1"
```

The version in the example is illustrative. Use the version actually recorded in `VERSION`. Sign commits/tags only when the maintainer has signing configured. Creating a local repository does not publish it; connect it to the maintainer's chosen remote when publication is authorized. Local Git history alone is not an off-device backup.

## Identify the version used for a translation

For future translation reports, record the package version from `VERSION`. When this is a Git checkout, also record the commit and whether tracked package files have uncommitted changes. Record the terminology/profile hashes using the existing run-evidence workflow, since external profiles and catalogs are not determined by the skill version.

```text
git rev-parse HEAD
git status --porcelain --untracked-files=normal
```

Report a modified checkout as `0.2.0 + local changes`, not as the unchanged tagged release. Report relevant untracked package additions separately; ignored caches do not change release identity. For an exported skill without `.git`, record the version and available package/input hashes without inventing a commit ID.

Historical runs retain their original identities and evidence. Do not retroactively assign the current version to an earlier run.

## Public release history

The public repository must contain only reviewed distribution files and synthetic examples in every reachable commit and tag. Keep private history backups outside the package; never merge them into the public repository. Check the [public distribution boundary](public-distribution.md) before publishing.
